# 本地深度视频组件

视频节点的“深度动作捕捉”在本机生成近白远黑的灰度参考视频。使用固定的 Video Depth Anything Small 模型，输入最多 15 秒，输出跟随原视频尺寸和比例；普通帧率保持不变，超过 30 fps 时转换为 30 fps。保存前读取实际输出的宽高与时长，竖屏和方形素材不再强制拉伸为横屏。

深度处理子进程复用桌面安装包内的 `ffprobe` 与 `ffmpeg`，启动时将已定位的工具目录加入子进程搜索路径；从 Finder 启动也无需另装系统媒体工具。Windows 深度组件自带工具目录仍保留。

桌面安装包不携带深度模型权重、Python、PyTorch 或已安装的深度运行环境，也不复制开发机的 `depth-runtime.json`。仅保留启动与按需安装所需的小型代码和元数据；普通编辑、模型渠道调用和项目管理无需下载深度组件。

内置 worker 的唯一编辑源为 `tools/depth-capture/depth_capture`；修改后运行 `python scripts/sync-depth-bootstrap-assets.py` 同步小型源码快照。桌面构建入口仅执行该脚本的 `--check` 模式，快照不一致时停止构建，不会为此安装深度依赖或下载模型。

首次使用时会先显示运行组件与模型的下载大小、需要预留的磁盘空间和存放位置，点击“下载深度捕捉组件/模型（国内镜像）”后才下载。也可以在“存储设置 → 深度捕捉组件”提前下载、暂停、继续或重新检查。无需自己安装 Python。空间不足时不能开始下载；释放空间后点击“重新检查”，或先迁移存储目录。

组件安装与深度任务分开管理。任务只读取已安装组件，不会自动补下载。暂停会保留下载缓存，退出应用后不会自行恢复下载；桌面应用重启后，未完成的深度任务保留原编号和输入，显示为已暂停，等待用户手动重试。CPU 处理可能较慢且占用较多内存。下载缓存、安装文件、临时解压和分片拼接都会占用空间。独立下载 Python 包时显示保守估算与安装阶段，不把估算大小当作精确下载总量；配置完整运行包清单时使用清单的实际大小。

组件下载与桌面更新共用代理选择规则：显式环境代理优先，否则读取 Windows/macOS 当前用户的静态系统代理，并保留排除地址规则。修改系统代理后重试会读取新配置，不需要在应用里重复填写代理。

Windows 默认模型先使用 `https://hf-mirror.com/depth-anything/Video-Depth-Anything-Small/resolve/main`，再尝试 Hugging Face 官方源；固定 Small 模型仍检查大小和 SHA256。Hugging Face 镜像仅分发模型，不分发 Python/PyTorch。Windows 默认在用户点击后独立下载 Python 与 Python 包，安装到应用当前数据目录，而不是系统 Python 或应用安装目录；这些依赖使用 Python、PyPI 与 PyTorch 官方软件源。该路径不需要部署者提供私有组件清单或发布密钥，也不连接旧产品云端服务。

部署方也可以通过 `BEEFTV_DEPTH_MANIFEST_URL` 显式配置完整运行包清单；Windows 保留这条路径原有的签名校验。生成这种清单时，通过 `CANVAS_DEPTH_RUNTIME_BASE_URL` 指定运行包资产基址，模型基址可通过 `CANVAS_DEPTH_MODEL_BASE_URL` 与 `CANVAS_DEPTH_MODEL_FALLBACK_BASE_URL` 配置。下载连接连续 30 秒没有收到数据时会切换到下一资产地址，保留已有文件供续传；文件全部下载后仍须通过大小和 SHA256 校验。暂停或退出应用不会触发切换，也不会在重启后自动恢复下载。

部署方也可以把已核验的模型放在本机目录，并通过 `CANVAS_DEPTH_MODEL_RUNTIME` 指向包含 `checkpoints/video_depth_anything_vits.pth` 的绝对路径。组件状态、下载预算、实际推理和设置页显示会使用同一个目录；模型仍按固定大小与 SHA256 检查，不因本地路径跳过校验。运行包继续位于工作区数据目录，设置页会分别显示组件目录与模型目录。

完整的外部本地组件可使用现有的 `BEEFTV_DEPTH_PYTHON`、`BEEFTV_DEPTH_TOOL_DIR`、`BEEFTV_DEPTH_RUNTIME` 三个变量；第三个变量指向模型根目录。三个变量必须同时设置，并作为一整组优先于持久配置。

桌面端也会读取工作区数据目录下的 `depth-runtime.json`。例如默认 Windows 数据目录对应 `%APPDATA%\MoyuCanvas\depth-runtime.json`；实际位置始终跟随应用当前 `dataDir`：

```json
{
  "version": 1,
  "python": "D:\\ENV\\depth-capture\\.venv\\Scripts\\python.exe",
  "toolDir": "D:\\ENV\\depth-capture\\worker",
  "modelRuntime": "D:\\ENV\\depth-capture\\models\\video-depth-anything-small\\v1"
}
```

该文件只接受版本 `1` 和以上四个字段，三个路径都必须是绝对路径。组件状态、用户触发的下载动作和任务执行共用同一解析结果：配置文件存在但格式、路径或资源校验失败时会显示错误并停止，不会转回托管下载。就绪检查要求 Python 普通文件、`toolDir/depth_capture` 目录、`toolDir` 同级 `vda/video_depth_anything/video_depth.py`，以及固定名称、大小和 SHA256 均匹配的 Small 模型权重。正式 worker 固定使用这个 VDA 源码目录并设置 `CANVAS_DEPTH_OFFLINE=1`；执行期间缺少源码或权重会直接失败，不会临时克隆仓库或下载模型。

手动下载模型时也沿用这套 HTTPS 代理和排除地址配置。暂时无法同步进度时不会把仍在运行的任务标成失败。重新打开画布会查询原任务，完成后取回结果，确认失败或暂停后可手动重试本地处理。失败详情保留进程末尾的错误原因，避免只显示下载进度。

迁移存储目录前会暂停组件下载并保留续传文件。有后台任务正在执行时，迁移会在关闭工作区前停止，提示先取消任务或等待完成，原工作区仍可使用。若关闭工作区本身失败，界面会说明迁移尚未开始、原数据所在位置和重启步骤，技术错误放在“错误详情”中。Windows 的深度处理、显卡检测和进程清理子进程不显示控制台窗口。

## 平台与 CUDA 社区测试

- Apple Silicon Mac 保持现有 MPS 路径。
- Windows x64 没有可用 NVIDIA GPU 时使用 CPU。
- 检测到 NVIDIA GPU 后，先运行真实 Small 模型探针，通过后才使用 CUDA。CUDA 设备错误最多回退 CPU 一次；若尚未安装 CPU 组件，会提示在存储设置中确认下载，组件页面会切换到所需的 CPU 包，不会自动追加下载。素材、下载、哈希或取消错误不会触发换设备重试。
- CUDA 包已通过构建与搬迁检查，但真实 NVIDIA 推理仍属社区测试。反馈时请提供显卡型号、驱动版本、应用版本、输入视频尺寸/时长和任务错误详情，勿附带密钥。

Windows CPU 在一台 AMD 显卡机器上完成了 2 秒和 15 秒合成视频验证，帧数分别为 60 和 450，输出全片可解码。该测试不能代表所有机器的性能或真实人物素材效果。

## 发布与回退

`release-depth-runtime.yml` 在官方 main 上构建 CPU 和 CUDA 包，经搬迁自检、CPU 真模型探针、逐文件/分片及完整包哈希检查后，发布不可覆盖的 `depth-runtime-v2` 组件 Release。CUDA 大包分为小于 2 GiB 的资产。

显式运行包清单由部署方提供并通过签名校验；用户视频存储与组件分发分开管理。未设置 `BEEFTV_DEPTH_MANIFEST_URL` 时，Windows 使用按钮触发的独立组件安装路径，其他平台仍需提供自己的组件分发配置。两种安装路径都不在生成任务中下载组件；已安装组件和通过 `CANVAS_DEPTH_MODEL_RUNTIME` 配置的已核验模型继续离线使用。

显式清单的签名使用部署方的 Ed25519 发布密钥。Windows 应用通过编译参数嵌入公钥，先验签清单，再校验下载文件；切换清单镜像仍使用同一公钥验签。选择该分发方式时，桌面发布流程需在构建时注入清单地址和对应密钥；默认的独立组件安装路径不依赖这组发布配置。

同一应用进程内的组件安装串行执行，避免不同任务共写缓存；推理不会被安装锁串行化。取消可中断安装等待、解压、文件校验及 Python/FFmpeg 进程树。

组件资产不覆盖。修复组件时使用新组件标签及新的受信清单地址，并发布引用该地址的新应用版本。桌面回退遵循自动更新发布文档，以更高版本号发布已知可用代码；不降低或覆盖已公开的版本。
